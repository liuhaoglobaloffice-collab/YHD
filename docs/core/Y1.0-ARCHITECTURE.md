### 3.2 Key Design Principles

#### Principle 1: Single Source of Truth
Every capability has exactly ONE authoritative implementation.

**Forbidden:**
`
core/
core_v2/
core_new/
core_final/
`

**Correct:**
`
core/
`

#### Principle 2: Provider ≠ Agent

**Provider:** AI model supplier (OpenAI, Anthropic, xAI, DeepSeek, Google, Moonshot)
**Agent:** AI employee (GPT, Grok, Claude, DeepSeek, Gemini, Kimi)

These are **strictly decoupled**.

#### Principle 3: Agent ≠ Workflow

**Agent:** Provides capability (research, analysis, coding)
**Workflow:** Orchestrates process (research → analyze → code)

#### Principle 4: Business ≠ Infrastructure

Business logic must NOT pollute Core.

#### Principle 5: Security First

All external access (Provider API, Network, Browser, External APIs) must go through **unified security boundaries**.

#### Principle 6: Approval First

High-risk operations require **human approval**:
`
Request → Identity → Permission → Policy → Approval → Execution
`

#### Principle 7: Fail Closed

Unknown state = **DENY by default**.

#### Principle 8: Audit Everything

All critical operations must be **auditable and traceable**.

#### Principle 9: Gateway Pattern

All external capabilities must go through gateways:
- AI Provider → Provider Gateway
- Network → Network Gateway
- Browser → Browser Gateway
- External API → External API Gateway

Agents CANNOT directly access the external world.

#### Principle 10: No Duplicate Architecture

Do NOT create a second system for new features.

Extend the existing architecture instead.

### 5.4 API Key Security

**API Keys MUST NEVER:**
- ❌ Be written in source code
- ❌ Be committed to Git
- ❌ Be stored in database
- ❌ Be written to logs
- ❌ Be written to test reports
- ❌ Be stored in regular config files
- ❌ Be returned to frontend

**API Keys CAN ONLY:**
- ✅ Be stored in environment variables
- ✅ Be stored in Secret Manager (Vault, AWS Secrets Manager)

System can only detect:
`python
credential_present = True
`

System CANNOT expose:
`python
credential_value = "sk-..."
`

#### 7.2.2 Critical Separation: Provider ≠ Agent

**Provider (供应商):**
- OpenAI
- Anthropic
- xAI
- DeepSeek
- Google
- Moonshot

**Agent (AI 员工):**
- GPT
- Claude
- Grok
- DeepSeek
- Gemini
- Kimi

**Why separation matters:**
1. An Agent can switch Providers (e.g., GPT can use OpenAI or Anthropic)
2. One Provider can serve multiple Agents
3. Providers can be added/removed without changing Agent logic
4. Cost tracking and fallback logic belong to Provider layer

**Provider Gateway Flow:**
`python
async def invoke(provider, model, messages, context):
    # 1. Security check
    if not security.check_boundary("provider_api"):
        raise SecurityError("Provider API disabled")
    
    # 2. Permission check
    if not rbac.check_permission(context.user, "provider.invoke"):
        raise PermissionError("No permission")
    
    # 3. Approval check
    if approval.requires_approval("provider_api_call"):
        approval_result = await approval.request(context, provider, model)
        if not approval_result.is_granted:
            raise ApprovalError("Approval not granted")
    
    # 4. Rate limit check
    if not rate_limiter.check(context.user, provider):
        raise RateLimitError("Rate limit exceeded")
    
    # 5. Cost check
    estimated_cost = cost_tracker.estimate(model, messages)
    if not cost_tracker.check_budget(context.user, estimated_cost):
        raise BudgetError("Cost budget exceeded")
    
    # 6. Select adapter
    adapter = get_adapter(provider)
    
    # 7. Invoke Provider API
    try:
        response = await adapter.invoke(model, messages)
    except Exception as e:
        # 8. Fallback strategy
        response = await fallback.handle(provider, model, messages, e)
    
    # 9. Track cost
    await cost_tracker.record(
        provider, model,
        response.input_tokens, response.output_tokens
    )
    
    # 10. Audit
    await audit.log("provider.api_call", context, provider, model, response)
    
    return response
`

## 18. Failure Handling & Recovery

### 18.1 Failure Categories

**Category 1: Transient Failures**
- Network timeouts
- Provider API rate limits
- Temporary unavailability

**Strategy:**
- Exponential backoff retry
- Max 3 retries
- Fallback to alternative provider

**Category 2: Permanent Failures**
- Invalid API key
- Insufficient permissions
- Invalid input

**Strategy:**
- No retry
- Log error
- Notify user
- Escalate if needed

**Category 3: System Failures**
- Database connection lost
- Redis unavailable
- Service crash

**Strategy:**
- Graceful degradation
- Circuit breaker
- Health check
- Auto-restart

### 18.2 Retry Policy

`python
retry_policy = {
    "max_attempts": 3,
    "initial_delay_ms": 1000,
    "max_delay_ms": 10000,
    "multiplier": 2.0,
    "jitter": True,
}

# Example:
# Attempt 1: immediate
# Attempt 2: wait 1000ms
# Attempt 3: wait 2000ms
# Attempt 4: wait 4000ms (max 3 attempts, so skip)
`

### 18.3 Circuit Breaker

`python
circuit_breaker = {
    "failure_threshold": 5,         # Open circuit after 5 failures
    "success_threshold": 2,         # Close circuit after 2 successes
    "timeout_seconds": 60,          # Try again after 60 seconds
}

# States: CLOSED, OPEN, HALF_OPEN
# CLOSED: Normal operation
# OPEN: Stop calling service, return error immediately
# HALF_OPEN: Allow limited requests to test recovery
`

### 18.4 Graceful Degradation

**Example: Knowledge search unavailable**
`python
try:
    results = knowledge_service.search(query)
except ServiceUnavailableError:
    # Fallback: Use cached results
    results = cache.get(query)
    if not results:
        # Fallback: Return empty results with message
        results = {
            "items": [],
            "message": "Knowledge service temporarily unavailable"
        }
`

## Appendix B: Decision Log

**Decision 1:** Use FastAPI instead of Django
- **Reason:** FastAPI provides better async support, automatic API documentation, type safety

**Decision 2:** Use PostgreSQL instead of MongoDB
- **Reason:** Relational data model fits better, ACID guarantees, mature ecosystem

**Decision 3:** Use Qdrant/Milvus instead of Pinecone
- **Reason:** Self-hosted option, cost control, data sovereignty

**Decision 4:** Separate Provider and Agent
- **Reason:** Decouple AI model supplier from AI employee role, enable provider switching

**Decision 5:** Separate Agent and Workflow
- **Reason:** Agent provides capability, Workflow orchestrates process, clear separation of concerns

**Decision 6:** Default deny for all external capabilities
- **Reason:** Security first, explicit opt-in, minimize attack surface

**Decision 7:** Require approval for high-risk operations
- **Reason:** Human oversight, prevent unintended consequences, cost control

**Decision 8:** Fail closed for unknown states
- **Reason:** Security first, prevent unintended access

**Decision 9:** Audit everything
- **Reason:** Compliance, debugging, cost tracking, security monitoring

**Decision 10:** No duplicate architecture
- **Reason:** Maintainability, single source of truth, avoid confusion
