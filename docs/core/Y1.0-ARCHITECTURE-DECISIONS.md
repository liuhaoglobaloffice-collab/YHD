## ADR-001: Separation of Provider and Agent

**Status:** Accepted  
**Date:** 2026-08-21  
**Decision Maker:** Architecture Team  

### Context

We need to design how the system interacts with AI model providers (OpenAI, Anthropic, xAI, etc.) and how we represent AI workforce roles (GPT, Grok, Claude, etc.).

### Decision

**Provider and Agent are strictly separated layers.**

**Provider:**
- Technical layer representing AI model suppliers
- Examples: OpenAI, Anthropic, xAI, DeepSeek, Google, Moonshot
- Responsibilities: API integration, cost tracking, rate limiting, fallback

**Agent:**
- Business/role layer representing AI employees
- Examples: GPT (AI Brain), Grok (Intelligence Brain), Claude (CTO)
- Responsibilities: Task execution, capability provision, role-specific logic

### Rationale

1. **Flexibility:** Agents can switch providers without code changes
2. **Maintainability:** Provider changes don't affect agent logic
3. **Testability:** Can mock providers without affecting agent tests
4. **Cost optimization:** Can route agents to cost-effective providers
5. **Resilience:** Provider failures can fallback without changing agent behavior

### Alternatives Considered

**Alternative 1: Merge Provider and Agent**
```python
class GPTAgent:
    def __init__(self):
        self.openai_client = OpenAI()  # Tightly coupled
```
- **Rejected:** Hard to switch providers, hard to test, inflexible

**Alternative 2: Agent calls Provider directly**
```python
class ResearchAgent:
    def research(self, query):
        response = openai.chat.completions.create(...)  # Direct call
```
- **Rejected:** No centralized cost tracking, no fallback, no security boundary

### Consequences

**Positive:**
- ✅ Agents are provider-agnostic
- ✅ Easy to add new providers
- ✅ Easy to switch providers
- ✅ Centralized cost tracking
- ✅ Centralized security boundary

**Negative:**
- ⚠️ Extra abstraction layer
- ⚠️ Slightly more complex initialization

## ADR-002: Separation of Agent and Workflow

**Status:** Accepted  
**Date:** 2026-08-21  
**Decision Maker:** Architecture Team  

### Context

We need to design how agents execute tasks and how multi-step processes are orchestrated.

### Decision

**Agent and Workflow are strictly separated.**

**Agent:**
- Provides capability (research, analysis, coding, writing)
- Stateless execution
- Can be invoked independently

**Workflow:**
- Orchestrates multi-step processes
- Defines sequence, parallelism, conditions
- Manages state and coordination

### Rationale

1. **Separation of concerns:** Agent focuses on "what", Workflow focuses on "how"
2. **Reusability:** Same agent can be used in different workflows
3. **Composability:** Workflows can compose multiple agents
4. **Maintainability:** Agent changes don't affect workflow logic
5. **Scalability:** Agents and workflows can scale independently

### Alternatives Considered

**Alternative 1: Agent contains workflow logic**
```python
class ResearchAgent:
    def execute(self, task):
        # Step 1: Collect data
        # Step 2: Analyze data
        # Step 3: Write report
        # Workflow logic embedded in agent
```
- **Rejected:** Agent becomes bloated, hard to reuse, hard to change workflow

**Alternative 2: Workflow contains agent logic**
```python
class ResearchWorkflow:
    def execute(self, task):
        # Direct API calls instead of using agents
        response1 = openai.chat.completions.create(...)
        response2 = anthropic.messages.create(...)
```
- **Rejected:** Duplicates agent logic, no agent reusability

### Consequences

**Positive:**
- ✅ Agents are simple and focused
- ✅ Workflows are flexible and composable
- ✅ Easy to add new workflows
- ✅ Easy to modify existing workflows
- ✅ Agent logic is reusable

**Negative:**
- ⚠️ Requires workflow engine
- ⚠️ Extra coordination layer

## ADR-003: Default Deny for External Boundaries

**Status:** Accepted  
**Date:** 2026-08-21  
**Decision Maker:** Security Team  

### Context

The system needs to call external APIs (Provider APIs, Network, Browser, External Services). We need to decide the default security posture.

### Decision

**All external boundaries are DISABLED by default.**

```python
boundary:
    provider_api_enabled: false
    network_enabled: false
    browser_enabled: false
    execution_enabled: false
    external_action_enabled: false
```

System must explicitly enable boundaries when needed.

### Rationale

1. **Security first:** Minimize attack surface
2. **Explicit opt-in:** Forces conscious decision
3. **Fail closed:** Unknown state = deny
4. **Cost control:** Prevents accidental expensive API calls
5. **Compliance:** Easier to audit what is enabled

### Alternatives Considered

**Alternative 1: Default allow**
```python
boundary:
    provider_api_enabled: true  # Enabled by default
```
- **Rejected:** Security risk, cost risk, accidental actions

**Alternative 2: Runtime check without config**
```python
if has_api_key("OPENAI_API_KEY"):
    # Automatically enable
```
- **Rejected:** Implicit behavior, hard to audit, security risk

### Consequences

**Positive:**
- ✅ Secure by default
- ✅ Explicit configuration required
- ✅ Clear audit trail
- ✅ Cost protection

**Negative:**
- ⚠️ Requires explicit enablement
- ⚠️ May be inconvenient during development

**Mitigation:**
- Provide development config with boundaries enabled
- Clear error messages when boundary is disabled

## ADR-004: Approval for High-Risk Operations

**Status:** Accepted  
**Date:** 2026-08-21  
**Decision Maker:** Security Team, Product Team  

### Context

Some operations are high-risk (expensive API calls, data deletion, external actions). We need to decide how to handle them.

### Decision

**High-risk operations require human approval.**

High-risk operations:
- Provider API calls
- Network requests
- Browser actions
- Code execution
- Data deletion
- External API calls

**Approval Flow:**
```
Request → Security Check → Approval Check → Execution
```

### Rationale

1. **Human oversight:** Prevent unintended consequences
2. **Cost control:** Expensive operations need approval
3. **Security:** High-risk actions need review
4. **Compliance:** Audit trail of approvals
5. **Flexibility:** Can disable approval for trusted operations

### Alternatives Considered

**Alternative 1: No approval, automatic execution**
```python
response = provider_gateway.invoke(...)  # Auto-execute
```
- **Rejected:** No human oversight, cost risk, security risk

**Alternative 2: Approval for everything**
```python
approval_required: true  # For all operations
```
- **Rejected:** Too much friction, impractical

**Alternative 3: Post-execution notification**
```python
# Execute first, notify later
response = provider_gateway.invoke(...)
notify_ceo(response)
```
- **Rejected:** Can't prevent unwanted actions

### Consequences

**Positive:**
- ✅ Human oversight for risky operations
- ✅ Cost control
- ✅ Security control
- ✅ Audit trail
- ✅ CEO has visibility and control

**Negative:**
- ⚠️ Adds latency for approved operations
- ⚠️ Requires approval UI
- ⚠️ CEO may need to approve frequently

**Mitigation:**
- Batch approvals
- Approval delegation
- Pre-approved policies
- Auto-approve for low-risk operations

## ADR-005: Use PostgreSQL for Relational Data

**Status:** Accepted  
**Date:** 2026-08-21  
**Decision Maker:** Architecture Team  

### Context

We need to choose a database for storing users, tasks, workflows, agents, approvals, audit logs, and business data.

### Decision

**Use PostgreSQL as the primary relational database.**

### Rationale

1. **ACID guarantees:** Critical for approvals, audit logs
2. **Mature ecosystem:** Well-established, reliable
3. **Rich query capabilities:** SQL for complex queries
4. **JSON support:** Can store semi-structured data
5. **Row-level security:** Organization-level isolation
6. **Performance:** Good performance for OLTP workloads
7. **Open source:** No vendor lock-in

### Alternatives Considered

**Alternative 1: MongoDB**
- **Pros:** Flexible schema, horizontal scaling
- **Cons:** No ACID (until recently), weak consistency, harder to query
- **Rejected:** Need ACID guarantees for critical operations

**Alternative 2: MySQL**
- **Pros:** Popular, good performance
- **Cons:** Weaker JSON support than PostgreSQL, less feature-rich
- **Rejected:** PostgreSQL has better JSON support and more features

**Alternative 3: SQLite**
- **Pros:** Simple, embedded, no server needed
- **Cons:** Not suitable for production, no concurrency
- **Rejected:** Not scalable for production

### Consequences

**Positive:**
- ✅ Strong ACID guarantees
- ✅ Rich query capabilities
- ✅ Mature and reliable
- ✅ Good performance
- ✅ Row-level security

**Negative:**
- ⚠️ Vertical scaling limitations (can be mitigated with read replicas)
- ⚠️ Schema migrations required

## ADR-006: Use Redis for Cache and Session

**Status:** Accepted  
**Date:** 2026-08-21  
**Decision Maker:** Architecture Team  

### Context

We need a caching layer for sessions, short-term memory, and rate limiting.

### Decision

**Use Redis for caching and session storage.**

### Rationale

1. **Performance:** In-memory, very fast
2. **Data structures:** Rich data structures (strings, hashes, sets, sorted sets)
3. **Expiration:** Built-in TTL support
4. **Pub/Sub:** Can be used for event bus
5. **Distributed locks:** Built-in support
6. **Mature:** Battle-tested

### Alternatives Considered

**Alternative 1: Memcached**
- **Pros:** Simple, fast
- **Cons:** Limited data structures, no persistence
- **Rejected:** Redis has more features

**Alternative 2: In-memory dictionary (Python)**
- **Pros:** No external dependency
- **Cons:** Not distributed, lost on restart
- **Rejected:** Not suitable for production

### Consequences

**Positive:**
- ✅ Fast caching
- ✅ Session storage
- ✅ Rate limiting
- ✅ Distributed locks
- ✅ Event bus (optional)

**Negative:**
- ⚠️ Memory-intensive
- ⚠️ Data lost on restart (unless persistence enabled)

## ADR-007: Use Qdrant or Milvus for Vector Database

**Status:** Accepted  
**Date:** 2026-08-21  
**Decision Maker:** Architecture Team  

### Context

We need a vector database for storing embeddings (documents, knowledge, memory).

### Decision

**Use Qdrant or Milvus as vector database.**

Prefer Qdrant for simplicity, use Milvus if advanced features needed.

### Rationale

1. **Self-hosted:** Data sovereignty, cost control
2. **Performance:** Fast vector search
3. **Scalability:** Can scale horizontally
4. **Metadata filtering:** Filter by metadata
5. **Open source:** No vendor lock-in

### Alternatives Considered

**Alternative 1: Pinecone**
- **Pros:** Managed service, easy to use
- **Cons:** Expensive, vendor lock-in, data stored externally
- **Rejected:** Cost and data sovereignty concerns

**Alternative 2: PostgreSQL with pgvector**
- **Pros:** No extra service, simple
- **Cons:** Slower vector search, limited scalability
- **Rejected:** Performance concerns for large-scale vector search

**Alternative 3: Elasticsearch**
- **Pros:** Can do vector search, good for full-text search
- **Cons:** Not optimized for vectors, resource-intensive
- **Rejected:** Not the best tool for vector search

### Consequences

**Positive:**
- ✅ Self-hosted, data sovereignty
- ✅ Cost control
- ✅ Good performance
- ✅ Open source

**Negative:**
- ⚠️ Requires self-hosting and maintenance
- ⚠️ Need to manage backups

## ADR-008: Use FastAPI for Backend

**Status:** Accepted  
**Date:** 2026-08-21  
**Decision Maker:** Architecture Team  

### Context

We need to choose a backend framework for building REST APIs.

### Decision

**Use FastAPI as the backend framework.**

### Rationale

1. **Async support:** Native async/await support
2. **Performance:** Very fast (on par with Node.js)
3. **Type safety:** Type hints and validation (Pydantic)
4. **Auto documentation:** Automatic OpenAPI/Swagger docs
5. **Modern:** Modern Python framework
6. **Easy testing:** Good testing support

### Alternatives Considered

**Alternative 1: Django**
- **Pros:** Mature, batteries-included, ORM
- **Cons:** Sync-first, slower, heavier
- **Rejected:** Not as performant for async workloads

**Alternative 2: Flask**
- **Pros:** Simple, flexible
- **Cons:** No async support (until recently), no auto documentation
- **Rejected:** FastAPI is more modern and feature-rich

**Alternative 3: Node.js (Express)**
- **Pros:** Good async support, large ecosystem
- **Cons:** Not Python, less type safety
- **Rejected:** Want to stay in Python ecosystem

### Consequences

**Positive:**
- ✅ Fast and modern
- ✅ Async support
- ✅ Type safety
- ✅ Auto documentation
- ✅ Easy testing

**Negative:**
- ⚠️ Less mature than Django
- ⚠️ Need to choose other libraries (ORM, migrations)

**Mitigation:**
- Use SQLAlchemy for ORM
- Use Alembic for migrations

## ADR-010: Layered Architecture (8 Layers)

**Status:** Accepted  
**Date:** 2026-08-21  
**Decision Maker:** Architecture Team  

### Context

We need to organize the system into logical layers with clear responsibilities.

### Decision

**Use 8-layer architecture:**

- Layer 0: Core Runtime
- Layer 1: Security & Governance
- Layer 2: Identity & Access
- Layer 3: AI Runtime
- Layer 4: Intelligence
- Layer 5: Execution
- Layer 6: Business
- Layer 7: CEO Command Center
- Layer 8: Observability (cross-cutting)

### Rationale

1. **Separation of concerns:** Each layer has clear responsibility
2. **Dependencies flow downward:** Higher layers depend on lower layers
3. **Maintainability:** Changes in one layer don't affect unrelated layers
4. **Testability:** Layers can be tested independently
5. **Security:** Security layer is enforced early (Layer 1)
6. **Scalability:** Layers can scale independently

### Alternatives Considered

**Alternative 1: Monolithic architecture**
```
All code in one layer
```
- **Rejected:** Hard to maintain, hard to test, hard to scale

**Alternative 2: Microservices from day 1**
```
Each module is a separate service
```
- **Rejected:** Over-engineering for Y1.0, adds complexity

**Alternative 3: Traditional 3-tier (Presentation, Business, Data)**
```
Frontend → Backend → Database
```
- **Rejected:** Not enough separation for our needs

### Consequences

**Positive:**
- ✅ Clear separation of concerns
- ✅ Maintainable
- ✅ Testable
- ✅ Scalable
- ✅ Security enforced early

**Negative:**
- ⚠️ More abstraction layers
- ⚠️ May feel over-engineered initially

**Future Evolution:**
- Y1.0: Layered monolith
- Y2.0: Can extract some layers into services if needed
- Y5.0: Full microservices (if needed)

## ADR-011: Single Source of Truth Principle

**Status:** Accepted  
**Date:** 2026-08-21  
**Decision Maker:** Architecture Team  

### Context

We need to prevent duplicate implementations of the same capability.

### Decision

**Every capability has exactly ONE authoritative implementation.**

Forbidden:
```
core/
core_v2/
core_new/
```

Correct:
```
core/
```

### Rationale

1. **Maintainability:** One place to fix bugs
2. **Consistency:** No conflicting behaviors
3. **Clarity:** Developers know where to find code
4. **Efficiency:** No duplicate effort

### Alternatives Considered

**Alternative 1: Allow duplicates, deprecate old**
```
core/         # Old
core_new/     # New
```
- **Rejected:** Confusing, which one to use? When to delete old?

**Alternative 2: Version in module name**
```
core_v1/
core_v2/
```
- **Rejected:** Still confusing, hard to maintain

### Consequences

**Positive:**
- ✅ Clear ownership
- ✅ No duplicate code
- ✅ Easy to find code
- ✅ Easy to maintain

**Negative:**
- ⚠️ Requires discipline
- ⚠️ Breaking changes need careful migration

**Enforcement:**
- Code review
- Naming conventions
- Documentation

## ADR-012: Fail Closed Security Policy

**Status:** Accepted  
**Date:** 2026-08-21  
**Decision Maker:** Security Team  

### Context

When the system encounters an unknown or uncertain state, we need to decide whether to allow or deny.

### Decision

**Fail closed: Unknown state = DENY.**

```python
def check_permission(user, action):
    policy = get_policy(user, action)
    if policy is None:
        return False  # Fail closed
    return policy.is_allowed
```

### Rationale

1. **Security first:** Better to be safe than sorry
2. **Explicit opt-in:** Forces conscious decision
3. **Reduces attack surface:** Unknown actions are blocked
4. **Compliance:** Easier to audit

### Alternatives Considered

**Alternative 1: Fail open (default allow)**
```python
if policy is None:
    return True  # Fail open
```
- **Rejected:** Security risk

**Alternative 2: Fail with error (no default)**
```python
if policy is None:
    raise PolicyNotFoundError()
```
- **Rejected:** Too strict, system becomes unusable

### Consequences

**Positive:**
- ✅ Secure by default
- ✅ Explicit policies required
- ✅ Reduced attack surface

**Negative:**
- ⚠️ May block legitimate actions if policy missing
- ⚠️ Requires complete policy definitions

**Mitigation:**
- Clear error messages
- Policy validation on startup
- Comprehensive policy templates

## ADR-013: Event-Driven Architecture

**Status:** Accepted  
**Date:** 2026-08-21  
**Decision Maker:** Architecture Team  

### Context

We need to coordinate between layers and modules (e.g., when a task is created, multiple systems need to react).

### Decision

**Use event-driven architecture with an Event Bus.**

```python
# Publisher
event_bus.publish(TaskCreatedEvent(task_id=...))

# Subscribers
@event_bus.subscribe(TaskCreatedEvent)
async def on_task_created(event):
    # Handle event
    pass
```

### Rationale

1. **Decoupling:** Publishers don't know subscribers
2. **Scalability:** Subscribers can scale independently
3. **Flexibility:** Easy to add new subscribers
4. **Auditability:** Events can be logged
5. **Async:** Non-blocking event handling

### Alternatives Considered

**Alternative 1: Direct method calls**
```python
task_service.create_task(...)
ai_team.start_task(...)
audit.log_task_created(...)
```
- **Rejected:** Tight coupling, hard to scale

**Alternative 2: Message queue (Kafka, RabbitMQ)**
```python
kafka.produce("task.created", ...)
```
- **Deferred:** Too heavy for Y1.0, may use in Y2.0

### Consequences

**Positive:**
- ✅ Decoupled modules
- ✅ Easy to extend
- ✅ Scalable
- ✅ Auditable

**Negative:**
- ⚠️ Eventual consistency
- ⚠️ Harder to debug (events are async)

**Implementation:**
- Y1.0: Redis Pub/Sub
- Y2.0+: Kafka/RabbitMQ if needed

## ADR-014: No Reuse from Old Project

**Status:** Accepted  
**Date:** 2026-08-21  
**Decision Maker:** CEO, Architecture Team  

### Context

There is an old project at `D:\LiuHao-AI`. We need to decide whether to reuse code from it.

### Decision

**Do NOT reuse any code from D:\LiuHao-AI.**

The old project is purely **historical reference**.

### Rationale

1. **Clean slate:** Avoid technical debt
2. **New architecture:** Old code doesn't fit new architecture
3. **Clarity:** No confusion between old and new
4. **Discipline:** Forces clean design decisions

### Alternatives Considered

**Alternative 1: Migrate code from old project**
```python
# Copy old code
from liuhaos_old import some_module
```
- **Rejected:** Technical debt, architectural mismatch

**Alternative 2: Gradual migration**
```python
# Keep old code, gradually replace
if feature_flag("use_new_code"):
    new_implementation()
else:
    old_implementation()
```
- **Rejected:** Too complex, confusing

### Consequences

**Positive:**
- ✅ Clean architecture
- ✅ No technical debt
- ✅ Clear separation

**Negative:**
- ⚠️ More initial work
- ⚠️ Can't leverage existing code

**Acceptance:**
- Faster long-term development
- Better maintainability
- Cleaner architecture
